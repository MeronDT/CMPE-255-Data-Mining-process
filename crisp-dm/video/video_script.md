# Video walkthrough script — CRISP-DM: hotel booking cancellations (≈ 12 min)

**Setup before recording:** the notebook open in Colab after *Run all* (outputs visible), the GitHub repo in a second tab, the deployed app in a third. Screen-record at 1080p; zoom the browser to ~125 %.

| Time | On screen | What to say (talking points) |
|---|---|---|
| 0:00–0:45 | Title cell | The problem: 37 % of bookings at two Portuguese hotels are cancelled. Rooms freed late stay empty; blanket overbooking risks turning guests away. Goal: flag risky bookings early. |
| 0:45–1:30 | CRISP-DM phase table | Six phases, each split into generic tasks with required outputs — the notebook has a heading for every output. CRISP-DM starts and ends with the business. |
| 1:30–3:00 | **Phase 1**: objectives, success criteria, cost/benefit table, data mining success criteria | Business criteria in euros; model criteria ROC-AUC ≥ 0.85 and precision ≥ 0.75 — fixed *before* modeling. Explain the €100 / −€100 cost model (avg booking ≈ €358) — it later chooses the decision threshold. |
| 3:00–5:00 | **Phase 2**: two source files, format problems, cancellation-rate charts, leakage suspects, Non Refund table | Two messy files ('NULL' strings, padded text, different types). City hotel cancels 42 % vs resort 28 %; lead time > 1 year → 68 %. The leakage detector flags `reservation_status` (it *is* the outcome) and parking (0 cancellations). Non Refund deposits cancel 99 % — 97 % are Portuguese group/tour-operator bookings with zero special requests: a data anomaly worth reporting, not a real "deposit effect". |
| 5:00–6:15 | **Phase 3**: exclusion log, cleaning log, derived attributes, integration checks | Every exclusion has a reason (known at booking time?). Duplicates kept, but they forced a change in validation (next phase). Integration validated against the published combined file — all checks pass. Time-based split: train on arrivals to April 2017, test on the latest 20 %. |
| 6:15–7:45 | **Phase 4**: fold dates, CV table, tuning | The story of the critic catch: shuffled CV said ROC-AUC 0.956; the real future test said 0.868. Duplicates and time drift inflate shuffled CV, so we switched to time-series folds. Random forest wins; tuning kept only because it beat the default on the same folds. |
| 7:45–10:00 | **Phase 5**: threshold chart, test metrics, confusion matrix, per-hotel table, feature importance, business table, sensitivity table | Threshold 0.34 chosen on training data only. Test: ROC-AUC 0.868, precision 0.77 → both criteria met. ≈ €19,700 per 1,000 bookings vs −€18,300 for flagging everything. Resort hotel recall lower (0.55 vs 0.73). Top drivers: country, deposit type, agent, special requests, lead time. Sensitivity test: what happens without country (possible leakage) — and the decision taken. |
| 10:00–11:15 | The deployed app | Score one booking (default ≈ 54 %); change deposit type to Non Refund and lead time to 300 → ≈ 94 %, flagged. Batch-score `sample_bookings.csv`. |
| 11:15–12:00 | Phase 6 monitoring plan + repo | PSI drift check and why seasonal features look "drifted"; retraining triggers; where everything is in the repo; lessons learned. |
